## confluenceSearchTool — отклонения от спецификации

Анализ соответствия `confluence_search` спецификации `GET /rest/api/content/search`
(`docs/api_docs.md`, раздел на строке 197).

Исходники:

- инструмент: `internal/server/confluence/read.go:149-183` (`Run`), `:632-639` (`McpTool`)
- фетчер: `internal/confluence/fetcher.go:165-187` (`Fetcher.Search`)
- конфиг: `internal/config/confluence.go:24,44`
- оригинальная Python-реализация (порт): `_old_python/src/mcp_atlassian/servers/confluence.py:192`,
  `_old_python/src/mcp_atlassian/confluence/search.py:87`

### Соответствие

| Элемент спецификации | Реализация | Вердикт |
| --- | --- | --- |
| `GET /rest/api/content/search` | `GET {BaseURL}/rest/api/content/search` (`V1BaseURL()`) | ✅ |
| `cql` (string, required) | всегда передаётся | ✅ |
| `limit` (int, default 25) | передаётся, default 10 | ✅ (default — допустимое отличие уровня инструмента) |
| `expand` (string) | `content.history,content.version` | ✅ синтаксически корректно |
| `start` (int, пагинация) | не поддерживается | ❌ |
| `cqlcontext` (string, optional) | не поддерживается | ⚠️ мелочь |
| **400** — невалидный CQL | `HTTPError` с телом ответа доходит до пользователя | ✅ |

DC-специфика учтена: вместо Cloud-only `siteSearch` (как в старом Python) используется
`text ~ "..."` — это более корректно для DC-спецификации.

### Пробелы и отклонения

1. **Нет пагинации — `start`** (`fetcher.go:165-187`, `read.go:151-183`)

   Спецификация описывает `start` и paged-ответ (`results`, `size`, `start`, `limit`,
   `_links`). Фетчер декодирует `size`, но выбрасывает всю мета-информацию, а инструмент
   возвращает голый массив. Получаются только первые `limit` результатов, и вызывающий
   не узнаёт, есть ли ещё. (limit ограничен описанием 1-50, т.е. >50 результатов
   принципиально недостижимы.)

2. **`limit` не клампится** (`read.go:156`)

   Описание аргумента обещает `1-50`, в Python было `ge=1, le=50` + `clamp_limit`.
   В Go `limit=1000` уходит в API как есть → возможный 400 или серверное ограничение.
   Описание инструмента не соответствует поведению.

3. **`CONFLUENCE_SPACES_FILTER` игнорируется в поиске**

   `ConfluenceConfig.SpacesFilter` читается из env (`internal/config/confluence.go:24,44`),
   но нигде не применяется: `confluenceSearchTool` использует только аргумент
   `spaces_filter` (`read.go:172-177`). В старом Python фильтр из конфига был
   «hard boundary», всегда AND-ится к CQL, а аргумент только сужал его. Сейчас
   операторский allowlist мёртв — это и регрессия, и риск (в shared-credential
   развёртываниях аргумент инструмента полностью определяет область поиска).

4. **Пустой query → 400 без валидации** (`read.go:155-170`)

   `query=""` + авто-режим даёт `text ~ ""` → невалидный CQL → 400 от API.
   `mcp.Required()` гарантирует только наличие ключа. Лучше вернуть понятную ошибку
   валидации до запроса.

5. **Хэвристика автоопределения CQL** (`read.go:161-166`, перенесена из Python)

   Проверки `" AND "` / `" OR "` case-sensitive: нижний регистр
   (`space in ("A") and type in ("page")` — без `=`, `~`, `>`, `<`) распознаётся как
   простой текст и оборачивается в `text ~ "..."`. И наоборот: обычный текст с `>`,
   `<` или `=` (например `a > b`) считается CQL → 400.

6. **Формат ответа отличается от Python** (не нарушение спеки, но изменение поведения)

   Python конвертировал результаты в `ConfluenceSearchResult` с обработкой excerpt
   HTML→markdown. Go возвращает сырые объекты API (включая expanded `history`/`version`)
   — excerpt остаётся сырым HTML, вывод заметно громоздче.

7. **Замечание по `expand`**

   Префикс `content.` задокументирован старым Python-комментарием для `/rest/api/search`;
   для `/content/search` дефолтный expand — `history,space,version`. Значение
   синтаксически валидно (неизвестные ключи молча игнорируются), нарушение спеки не
   составляет, но реальный набор полей в результатах зависит от дефолтов API.

### Рекомендации (по приоритету)

- [ ] **1.** Вынести `start` и вернуть мета-пагинацию в ответ (`size`, `has_more`) —
      либо явно задокументировать «только первые N результатов».
- [ ] **2.** Клампить `limit` в 1-50 — привести поведение в соответствие с описанием.
- [ ] **3.** Применять `cfg.SpacesFilter` как AND-границу (как в Python) — или убрать
      env из конфига, если не нужен.
- [ ] **4.** Валидировать пустой `query` до обращения к API.
- [ ] **5.** Опционально: case-insensitive матчинг ` and ` / ` or ` в хэвристике
      (с осторожностью — ложные срабатывания на обычном тексте).

Пункт 3 — самый существенный: это единственное, что ломает заявленное поведение
конфигурации, а не просто сужает возможности.
